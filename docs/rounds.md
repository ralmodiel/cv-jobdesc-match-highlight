34. Security (decompression bombs): a 15 MB upload can unpack to many gigabytes. A Word file is a zip that declares each part's unpacked size, and JSZip believed it until the part ended, so a part declared small that really unpacked to 3 GB took 15–18 s and gigabytes of memory before failing. Each part is now counted as it unpacks and refused once it passes its declared size or the 60 MB total: a 14 GB bomb in document.xml or fontTable.xml is refused in 1.6 s as damaged. A PDF stream declares no size, so every way pdf.js and pdf-lib unpack one now stops at 256 MB (a 48 MP photo stored losslessly is 144 MB): pdf.js's own filters, its Brotli decoder, the browser's DecompressionStream, and pdf-lib's filters. The browser's stream is fed 64 KB at a time, since it unpacks each written chunk whole (a 14 GB page written in one go crashed the tab despite the cap). The patches are applied at build time, and the build fails if an update changes the patched code. The text before the cut is kept for matching. Downloading such a file as PDF is refused with a message to choose Word, since the rebuilt page would lose the whole stream. 14 GB bombs through the built app: one added to page 1's contents gets that message after 28 s (it crashed the tab at 34.7 s before), and a page 2 made only of a bomb is drawn in 4.6 s (with the cap but without the 64 KB feed, it crashed at 32.8 s). The app also stopped hiding its own build messages: every failed build showed the general "could not be created" text, so the message for a password-protected PDF never appeared. check-browser 49 (new: a Word part that unpacks past its declared size is refused; a PDF stream past 256 MB is read up to the cap and not rebuilt as PDF).
35. Security (image bombs): an image in a PDF can be small as a file and huge once decoded, and its own header can claim a larger size than the PDF states. Ten such files through the built app (a 2 kB JPEG whose header claims 65500 × 65500, a 20000 × 20000 JPEG that the PDF calls 100 × 100, a 20000² image of zeros, a JPEG 2000 header claiming 65500², JBIG2, an 81 MP image) never crashed the desktop tab, but took up to 6 s and 3 GB of memory, enough to crash a phone's. Reading now skips images, since it needs only the text. The preview leaves out any image over 50 MP by the size the PDF states, and two build-time patches stop pdf.js's JPEG and JPEG 2000 decoders before they allocate, when the image's own header passes 50 MP. The preview also tells pdf.js to shrink images past 16 Mpx (iOS's canvas limit) as they decode. Without that number, pdf.js finds the browser's canvas limit by trying canvases of up to 1 GB, which a large image's header set off: 1.3 s and about 1 GB each time. All ten now finish in 0.6–1.1 s at 500–720 MB, the same as a page with no image. A left-out image is only missing from the preview, and the download keeps it. Reading a CV with a 12 MP photo takes the same time as before in Chromium and Firefox, because pdf.js decodes images after it hands back the page. check-browser 51 (new: a 4800 × 3600 photo is still drawn in the preview; a JPEG whose header claims 65500 × 65500 is left out before it decodes).
